# Generic 240×240 IPS ST7789 Display — Pi Zero W Setup Notes

This panel cost us hours. Everything you need to know lives here so it doesn't happen again.

## Hardware

- Generic AliExpress 1.3" 240×240 IPS display
- Controller: **ST7789V** (no markings on PCB; identified by behaviour)
- 7-pin header: `GND, VCC, SCL, SDA, RES, DC, BLK`
- **No CS pin** — CS is internally tied to GND on the PCB, so the panel is always selected. Don't try to drive CS; just leave SPI0's CE0/CE1 lines unwired.
- Operating voltage: **3.3 V** (never 5 V — this is logic+panel; backlight is also fed from VCC)
- Write-only: no MISO from the panel.

## Wiring on the Pi Zero W (direct, no cobbler/breadboard)

| Display pin | Pi header pin | Pi GPIO (BCM) | Function |
|-------------|--------------:|--------------:|----------|
| GND         | 9             | —             | Ground |
| VCC         | 17            | —             | 3.3 V |
| SCL         | 23            | GPIO 11       | SPI0 SCLK |
| SDA         | 19            | GPIO 10       | SPI0 MOSI |
| RES         | 22            | GPIO 25       | Hard reset |
| DC          | 18            | GPIO 24       | Data / Command select |
| BLK         | 33            | GPIO 13       | Backlight (PWM-capable) |

`MISO` (Pi pin 21, GPIO 9) is unused. SPI0 `CE0` (pin 24, GPIO 8) and `CE1` (pin 26, GPIO 7) are also unused — leave them disconnected.

Other GPIOs used on this Pi (don't reuse): GPIO 6 = "back" button, GPIO 26 = "next" button.

## ⚠️ Critical: SPI mode

**This panel only works in SPI mode 2 or 3. Modes 0 and 1 produce a completely black screen.**

The ST7789 datasheet claims to support modes 0 and 3. In practice, with jumper-wire setups, mode 0's idle-LOW clock can glitch during init and the panel ignores everything. Mode 3 sidesteps that.

```python
spi.mode = 3      # MUST be 2 or 3, NOT 0
```

### SPI mode reference (general)

| Mode | CPOL | CPHA | Clock idles | Data sampled on |
|-----:|:----:|:----:|:-----------:|:----------------|
|  0   |  0   |  0   | LOW         | rising edge     |
|  1   |  0   |  1   | LOW         | falling edge    |
|  2   |  1   |  0   | HIGH        | falling edge    |
|  3   |  1   |  1   | HIGH        | rising edge     |

Modes 2 and 3 both idle the clock HIGH — that's the property this panel needs.

## ⚠️ Library compatibility

The Pimoroni `st7789` Python library **hard-codes SPI mode 0** — it will NOT work with this panel. Adafruit/CircuitPython variants also default to mode 0. Use direct `spidev` + `lgpio` from a Python venv instead.

## Boot / system prerequisites

In `/boot/firmware/config.txt`:
```
dtparam=spi=on
```
After enabling, reboot. Verify with:
```bash
ls /dev/spidev0.*       # should show spidev0.0 and spidev0.1
lsmod | grep spi        # should show spidev and spi_bcm2835
```

User `hypnoshock` is already in groups `spi` and `gpio` (no further setup needed). Python venv lives at `~/mod_player/.venv`.

## Color format

- RGB565, 16-bit, **high byte first** (big-endian)
- Bit layout: `RRRRR GGGGGG BBBBB`
- Useful values:

| Color | RGB565 | Bytes sent |
|-------|--------|------------|
| Red   | 0xF800 | 0xF8, 0x00 |
| Green | 0x07E0 | 0x07, 0xE0 |
| Blue  | 0x001F | 0x00, 0x1F |
| White | 0xFFFF | 0xFF, 0xFF |
| Black | 0x0000 | 0x00, 0x00 |

With `MADCTL = 0x00` this panel renders in **RGB order** — no R/B swap needed. (Originally suspected one, but the real issue was just the SPI mode.)

## Initialization sequence

```
Hard reset:
  RST high   wait 50 ms
  RST low    wait 100 ms
  RST high   wait 150 ms

Software:
  0x01 SWRESET        wait 200 ms
  0x11 SLPOUT         wait 600 ms
  0x3A COLMOD  + 0x55              (16-bit RGB565)
  0x36 MADCTL  + 0x00              (RGB, normal orientation)
  0x21 INVON                       (required for ST7789)
  0x2A CASET   + 0x00,0x00,0x00,0xEF   (cols 0..239)
  0x2B RASET   + 0x00,0x00,0x00,0xEF   (rows 0..239)
  0x13 NORON          wait 20 ms
  0x29 DISPON         wait 100 ms

Pixel data:
  0x2C RAMWR  + 240*240*2 bytes of RGB565
```

DC line: LOW for command byte, HIGH for data byte(s). Toggle DC before every transfer.

## Minimal working snippet (mode 3, direct driver)

```python
import spidev, lgpio, time

DC, RST, BL = 24, 25, 13
h = lgpio.gpiochip_open(0)
lgpio.gpio_claim_output(h, DC, 0)
lgpio.gpio_claim_output(h, RST, 1)
lgpio.gpio_claim_output(h, BL, 1)

spi = spidev.SpiDev()
spi.open(0, 0)
spi.mode = 3                              # <-- critical
spi.max_speed_hz = 4_000_000

def cmd(c):
    lgpio.gpio_write(h, DC, 0)
    spi.writebytes([c])

def data(d):
    lgpio.gpio_write(h, DC, 1)
    if isinstance(d, int):
        spi.writebytes([d])
    else:
        for i in range(0, len(d), 2048):
            spi.writebytes2(d[i:i + 2048])

# Hard reset
lgpio.gpio_write(h, RST, 1); time.sleep(0.05)
lgpio.gpio_write(h, RST, 0); time.sleep(0.10)
lgpio.gpio_write(h, RST, 1); time.sleep(0.15)

# Init
cmd(0x01); time.sleep(0.20)
cmd(0x11); time.sleep(0.60)
cmd(0x3A); data(0x55)
cmd(0x36); data(0x00)
cmd(0x21)
cmd(0x2A); data([0, 0, 0, 0xEF])
cmd(0x2B); data([0, 0, 0, 0xEF])
cmd(0x13); time.sleep(0.02)
cmd(0x29); time.sleep(0.10)

# Fill red
cmd(0x2C)
data(list(bytes((0xF8, 0x00)) * (240 * 240)))
```

## Troubleshooting checklist (in order)

1. **`/dev/spidev0.0` exists and `spi_bcm2835` is loaded.**
2. **SPI mode is 2 or 3.** This single bit was the root cause of multi-hour debugging. Default mode 0 = black screen.
3. **No jumper stacking on one Pi pin.** Female-female dupont connectors lose contact when stacked — push only one wire onto each header pin. If you must tap a pin, use a breadboard tie point so each wire bites independently.
4. **Wire continuity end-to-end.** Pi pin works on its own isn't enough — the *wire* from Pi pin to display pad must also conduct.
5. **Right pin assignment.** GPIO 24 = DC, GPIO 25 = RES. Adjacent header pins (16/18/20, 21/22/23) are easy to mis-count under a dense header.
6. **Power.** 3.3 V only. Backlight working tells you VCC+GND are fine but says nothing about the signal lines.

## Useful debug techniques

- **SPI loopback (MOSI ↔ MISO, pin 19 ↔ pin 21).** Send a pattern, read it back: if it matches, SPI hardware + clock + MOSI/MISO pins are all functional regardless of any external device.
- **GPIO-via-MISO loopback.** Jumper any GPIO under test to pin 21, claim it as output via `lgpio`, toggle high/low, read MISO via `spi.xfer2([0x00]*N)`. 0xFF means the pin is going high, 0x00 means it's stuck low. Proves each control pin is actually driving its line.
- **Start slow.** 1 MHz SPI is forgiving; speed up only after function is confirmed at low speed. Don't chase a flaky high-speed setup before you've made it work slowly.
- **Distinct-color frames.** Don't sweep through colors faster than ~5 s each when a human is in the loop — they need time to look up from the keyboard.

## Things that did NOT cause our failure (but might in future)

- Pimoroni library's `gpiodevice` chip selection: it does find the right chip on Pi Zero W (`gpiochip0`).
- Wire length / SPI speed: at 4 MHz with ~10 cm jumpers, signal integrity is fine.
- BGR/RGB color swap: this panel is RGB with `MADCTL = 0x00`. Reds are reds.
- 240×320 GRAM offset: this panel is genuinely 240×240 internally; no `offset_top=80` needed.
- vc4-kms-v3d framebuffer driver being loaded: doesn't interfere with spidev access.
